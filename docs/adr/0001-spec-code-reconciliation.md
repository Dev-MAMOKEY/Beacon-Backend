# 명세서와 코드가 어긋날 때: 명세서가 목표, 실배포 기능은 역문서화

기능명세서 v2.x는 **의도한 설계(목표)**를 나타낸다. 명세서와 구현이 어긋날 때는 원칙적으로 **코드를 명세서에 맞춘다**(아직 안 만든 부분은 명세서를 목표로 유지하고 슬라이스 이슈로 추적). 단 예외로, **이미 배포되어 동작 중인 실기능**(예: `POST /clubs/create`, `PATCH /clubs/soft-delete/{clubId}`, `PATCH /members/me/fcm-token`)은 명세서에 **역으로 추가**해 문서를 현실과 일치시킨다.

명시적 반례 한 가지: **초대코드 자릿수**는 명세서(6)가 아니라 **운영 현실(4)을 정답으로 확정**했다. 따라서 명세서를 4로 정정하고, 아직 6을 생성하는 백엔드(`InviteService.CODE_LENGTH`)는 4로 바꾸는 이슈를 별도로 낸다.

이유: 명세서를 "코드에 100% 맞추기"로 하면 미구현·버그(비콘 설정 부재, export가 CSV/Excel 아닌 JSON, 세션 시작 1분 뒤 자동종료 등)까지 문서가 정당화해버린다. 반대로 "명세서 절대주의"는 팀이 이미 합의해 배포한 기능을 문서가 부정하게 된다. 그래서 **목표 = 명세서, 단 확정된 현실은 개별적으로 명세서에 반영**하는 절충을 택했다. 이 판단은 grill 세션(2026-07-05)에서 사용자가 "타깃 + 실배포 반영"을 선택해 확정됐다.
